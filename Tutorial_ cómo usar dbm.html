Tutorial: cómo usar dbm

Esta guía te lleva paso a paso desde cero hasta tener un proyecto con migraciones, cambios de datos y seeds corriendo contra PostgreSQL (el mismo flujo aplica a MongoDB, con las diferencias que se marcan en cada sección).

1. Instalación

Descomprime dbm.zip y prepara el proyecto:

cd dbm
pnpm install
pnpm build

Esto genera dist/. A partir de aquí puedes invocar la CLI de dos formas:

# Opción A: exponer el comando "dbm" globalmente
pnpm link --global
dbm --help

# Opción B: sin link, llamando directo al archivo compilado
node dist/cli/cli.js --help

En el resto del tutorial usamos dbm, pero puedes reemplazarlo por node dist/cli/cli.js si no hiciste el link global.

Windows y pnpm: pnpm no sirve para ejecutar un archivo .js: pnpm .\dist\cli\cli.js ... falla con "no es una aplicación Win32 válida". Usa node .\dist\cli\cli.js ... o el comando dbm tras el link global. Si pnpm link --global se queja del directorio global, ejecuta antes pnpm setup y abre una terminal nueva. Para deshacer el link: pnpm uninstall --global @dbm/cli.

2. Crear un proyecto nuevo

dbm project create ubipark --driver postgres

Esto crea:

ubipark/
├── dbm.yaml
├── migrations/
├── data/
└── seeds/
    ├── development/
    └── test/

Para un proyecto Mongo sería --driver mongo.

2.1 Configurar la conexión

Abre ubipark/dbm.yaml:

project: ubipark

database:
  driver: postgres
  version: 17          # versión que ESPERAS usar

  connection:
    host: ${DB_HOST}
    port: 5432
    database: ubipark
    username: ${DB_USER}
    password: ${DB_PASSWORD}

  schema: ubipark
  onVersionMismatch: error   # error | warn | ignore

migrations:
  path: ./migrations
data:
  path: ./data
seeds:
  path: ./seeds

Las credenciales nunca van escritas en el archivo: se resuelven desde variables de entorno.

export DB_HOST=localhost
export DB_USER=postgres
export DB_PASSWORD=postgres

No hace falta exportarlas a mano: dbm project create genera un .env junto al dbm.yaml y dbm lo carga solo. Una variable ya exportada en la terminal (o inyectada por CI) siempre gana sobre el .env. Para otros entornos puedes añadir un .env.production (ver sección 12). Ambos están en el .gitignore del proyecto.

Mongo: en vez de host/port/username/password, usas connection.uri (ej. ${MONGO_URI} = mongodb://localhost:27017) y connection.database.

2.2 Validar que todo esté bien

cd ubipark
dbm validate ubipark

Deberías ver algo así:

✓ Configuration
✓ Database connection
✓ Database engine — postgres
✓ Database version — configured 17 / detected 17.5
✓ Migration numbering
✓ Duplicate migrations
✓ Checksums
✓ Migration history
✓ Driver compatibility

Si Database version marca ✗, significa que el motor real no coincide con lo configurado. Ajusta database.version en el dbm.yaml o instala/usa la versión correcta.

3. Crear tu primera migración estructural

dbm migration create ubipark create_parkings

Esto crea migrations/001_create_parkings.sql con un esqueleto. Edítalo:

-- dbm:meta
-- irreversible: false
-- dbm:end

CREATE TABLE parkings (
    id         SERIAL PRIMARY KEY,
    nombre     TEXT NOT NULL,
    capacity   INTEGER,
    deleted_at TIMESTAMPTZ
);

Si quieres que sea reversible, crea también el archivo de "down" con el mismo nombre + .down:

cat > migrations/001_create_parkings.down.sql << 'EOF'
DROP TABLE parkings;
EOF

Si no creas el .down.sql, dbm marca automáticamente la migración como irreversible (no podrás hacer rollback de ella, y no fingirá que puede).

Bloque de metadata (opcional)

Al inicio de cualquier archivo (SQL o TS) puedes declarar:

-- dbm:meta
-- irreversible: true
-- requires:
--   postgres:
--     minVersion: 15
-- dbm:end
  • irreversible: true → bloquea el rollback aunque exista un .down.sql.
  • requires → exige una versión mínima/máxima del motor. Si el proyecto usa una versión menor, dbm validate / dbm migrate fallan con el mensaje exacto de qué versión hace falta.

Mongo: en vez de .sql, tus migraciones son .ts con export async function up(db) {...} y opcionalmente down(db). El mismo bloque de metadata funciona con // en vez de --.

4. Ejecutar migraciones

dbm migrate ubipark

En local no hace falta escribir --env: por defecto vale development. Antes de migrar, dbm imprime una línea Target: ubipark → postgres host:5432/base (env: development) para que veas contra qué base vas a operar. Mira la sección 12 para saber cuándo sí usar --env.

Salida esperada:

Migrations
  ✓ 001_create_parkings (4ms)

Si vuelves a correr el mismo comando, no pasa nada (ya está aplicada):

Migrations
  - 001_create_parkings (ya ejecutada)

Dry-run

Para ver qué se ejecutaría sin tocar la base:

dbm migrate ubipark --dry-run

Ver el estado

dbm status ubipark

Project: ubipark
Driver: postgres  |  Configured: 17  |  Detected: 17.5

┌───────────┬─────────┬──────────────────┬──────────┐
│ Type      │ Version │ Name             │ Status   │

5. Migraciones de datos (cambiar datos existentes)

Distinto de una migración estructural: aquí transformas datos ya cargados.

dbm data create ubipark normalize_names

Edita data/002_normalize_names.sql:

-- dbm:meta
-- irreversible: true
-- dbm:end

UPDATE parkings
SET nombre = TRIM(nombre)
WHERE nombre IS NOT NULL;

Y para un soft delete:

dbm data create ubipark deactivate_old_parkings

-- dbm:meta
-- irreversible: false
-- dbm:end

UPDATE parkings
SET deleted_at = CURRENT_TIMESTAMP
WHERE nombre = 'Parking Obsoleto';

cat > data/003_deactivate_old_parkings.down.sql << 'EOF'
UPDATE parkings SET deleted_at = NULL WHERE nombre = 'Parking Obsoleto';
EOF

Corre todo junto con dbm migrate (migrations + data changes se ejecutan en la misma orden numérica dentro de cada categoría):

dbm migrate ubipark

6. Seeds (datos iniciales / de prueba)

dbm seed create ubipark parkings_demo

Sin --env el seed se crea para development. Esto crea seeds/development/001_parkings_demo.sql. Diséñalo para ser idempotente si planeas re-ejecutarlo:

INSERT INTO parkings (nombre, capacity)
SELECT 'Parking Centro', 120
WHERE NOT EXISTS (SELECT 1 FROM parkings WHERE nombre = 'Parking Centro');

Ejecutarlo (usa development por defecto):

dbm seed ubipark

Si necesitas re-correrlo (porque es idempotente):

dbm seed ubipark --rerun

Aquí --env solo hace falta para seeds de otro entorno, por ejemplo los de seeds/test/:

dbm seed create ubipark parkings_demo --env test
dbm seed ubipark --env test

Un seed guardado en seeds/development/ nunca se ejecuta si corres --env production, porque --env elige la carpeta seeds/<env>/. Además, production es un entorno protegido: dbm seed en ese entorno pide confirmación (ver sección 12).

7. Rollback

dbm rollback ubipark --steps 1

Reglas importantes:

  • Revierte en orden cronológico inverso (lo último ejecutado primero).
  • Si encuentra una migración marcada irreversible en el camino, se detiene ahí y no sigue revirtiendo lo anterior — no finge que puede recuperar datos que no puede recuperar.
  • Si quieres corregir algo ya ejecutado, la recomendación del spec es no tocar el archivo original: crea una migración nueva que corrija lo necesario (dbm migration create ubipark fix_normalized_names).

8. Validación de compatibilidad de motor

Si una migración necesita, por ejemplo, PostgreSQL 15+:

-- dbm:meta
-- requires:
--   postgres:
--     minVersion: 15
-- dbm:end

y tu proyecto está en PostgreSQL 13, dbm validate (o dbm migrate) falla así:

✗ Driver compatibility — 004_create_feature_x requiere feature ... no disponible

o, si es un requisito de versión general:

ERROR
Migration 008_create_feature_x requires postgres >= 15.
Current version: 13

Exit code: 3 (incompatibilidad de versión).

9. Uso en CI/CD

dbm migrate ubipark --env production --non-interactive

En CI usa los dos flags. --env production carga .env.production (si existe) y etiqueta el historial. --non-interactive es necesario porque production es un entorno protegido: dbm pide confirmación antes de modificarlo y, sin terminal y sin el flag, falla con código 1 en vez de quedarse esperando. En CI las credenciales siguen viniendo de las variables (DB_HOST, DB_USER, DB_PASSWORD), que tienen prioridad sobre cualquier .env.

Revisa el código de salida en tu pipeline:

Código Significado
0 Éxito
1 Error genérico
2 Configuración inválida
3 Incompatibilidad de versión
4 Checksum inválido (archivo modificado tras ejecutarse)
5 Migration lock (ya hay una ejecución en curso)

Ejemplo en GitHub Actions:

- name: Run migrations
  env:
    DB_HOST: ${{ secrets.DB_HOST }}
    DB_USER: ${{ secrets.DB_USER }}
    DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
  run: |
    cd ubipark
    dbm migrate ubipark --env production --non-interactive

10. Qué pasa si alguien modifica un archivo ya ejecutado

Si editas 001_create_parkings.sql después de que ya se ejecutó, el checksum cambia y dbm lo detecta:

ERROR
Migration 001_create_parkings fue modificada después de haberse ejecutado.
Expected checksum: 8d33fc17...
Current checksum:  2bafc4b8...

La ejecución se detiene (exit code 4). La forma correcta de corregir un error es crear una nueva migración, no editar la vieja.

11. Múltiples proyectos y motores en el mismo repo

No hay nada especial que hacer: cada proyecto es una carpeta con su propio dbm.yaml. Puedes tener, por ejemplo:

ubipark/      (postgres 17)
legacy-app/   (postgres 13)
trainers/     (mongo 8)

y correr los comandos apuntando a cada uno:

dbm migrate ubipark
dbm migrate legacy-app
dbm migrate trainers

dbm project list (corrido desde el directorio que contiene todas las carpetas) te muestra cuáles detecta:

dbm project list

12. Entornos: --env y --non-interactive

Regla corta: en local no necesitas escribir ninguno de los dos. Se usan para apuntar a otros entornos (staging, production) y en CI/CD.

Cómo se elige el entorno

El entorno efectivo es, en este orden: el flag --env, la variable DBM_ENV, o development. Sirve para tres cosas:

  1. Elegir la conexión. Con --env production se carga .env.production (si existe) antes que .env. Prioridad: variables exportadas en la terminal > .env.<entorno> > .env.
  2. Elegir los seeds de la carpeta seeds/<entorno>/.
  3. Etiquetar el historial (columna environment de dbm_history).

Ejemplo: tu .env apunta a la base local y .env.production solo redefine lo que cambia:

# .env
DB_HOST=localhost
DB_USER=postgres
DB_PASSWORD=postgres
DB_NAME=ubipark_dev

# .env.production
DB_HOST=prod.miservidor.com
DB_USER=app
DB_PASSWORD=...
DB_NAME=ubipark

Para que DB_NAME funcione, en el dbm.yaml escribe database: ${DB_NAME}. Con eso:

dbm migrate ubipark                  # base local (.env)
dbm migrate ubipark --env production # base de producción (.env.production)

Cada migrate, rollback y seed imprime Target: ... con el motor, host y base (sin contraseñas). Léelo antes de confirmar.

Qué comandos usan --env

ComandoEfecto de --env¿Hace falta escribirlo?
migrate, rollbackCarga .env.<entorno>, etiqueta el historial y aplica la protección de entornos.Solo para apuntar a otro entorno (production, staging).
seed, seed createElige la carpeta seeds/<entorno>/ y carga .env.<entorno>.Solo si no es development (p. ej. --env test).
statusCarga .env.<entorno> y lista los seeds de ese entorno.Solo para consultar otro entorno.
validate, database version, project ..., migration create, data createNo aceptan --env.No existe.

Entornos protegidos y --non-interactive

Por defecto production es un entorno protegido (se puede cambiar con protectedEnvironments: [production, staging] en el dbm.yaml). Antes de migrate, rollback o seed en un entorno protegido, dbm pide escribir el nombre del entorno:

Target: ubipark → postgres prod.miservidor.com:5432/ubipark (env: production)
⚠ Vas a modificar un entorno protegido (production).
Escribe "production" para continuar:
  • Si escribes otra cosa, se cancela (código 1) y no se toca la base.
  • --dry-run nunca pide confirmación, porque no modifica nada.
  • --non-interactive salta la confirmación. Úsalo solo en CI/CD o en scripts.
  • Sin terminal interactiva y sin --non-interactive, el comando falla con código 1 en vez de quedarse esperando.
  • En entornos no protegidos (development, test) --non-interactive no cambia nada, así que no lo escribas.

Cuidado: si apuntas a producción exportando variables (por ejemplo DB_HOST) pero escribes --env development (o nada), dbm no te pedirá confirmación, porque la protección depende del entorno y no de la base real. Por eso conviene usar siempre --env production con la base de producción y revisar la línea Target.

SituaciónComando

13. Referencia rápida de comandos

dbm project list
dbm project create <name> --driver postgres|mongo

dbm migration create <project> <name>
dbm data create <project> <name>
dbm seed create <project> <name> [--env <env>]   # --env solo si no es development

dbm migrate <project> [--env <env>] [--dry-run] [--non-interactive]
dbm rollback <project> [--steps N] [--env <env>] [--non-interactive]
dbm seed <project> [--env <env>] [--dry-run] [--rerun] [--non-interactive]
# --env solo hace falta si no es development; --non-interactive solo en CI/entornos protegidos

dbm status <project> [--env <env>]
dbm validate <project>
dbm database version <project>

Ejemplos completos incluidos
